# Declarative API lifecycle decisions

Reviewed against published Archestra 1.4.0-rc.48 and its backend route/model contracts. These decisions distinguish persistent configuration from alternate endpoints, observations and commands. They are a design and implementation queue; a row marked desired is not claimed as tested support.

The baseline at b180fee contains 29 fully exercised families in both scopes. The expansion adds six native-tested families: hook, default-user-limit, directory, external gateway profile, service account and service-account token. All six pass real create/update/drift-repair/delete reconciliation in both scopes; runtime evidence is recorded separately in `crossplane-persistent-extensions.json`. Both Linux runtime images and embedded packages pass `runtime-package-validation.json`.

|---|---|---|---|
| LLM proxies and profiles | External `profile` subtype as `archestra_llm_proxy_profile`, with inbound identity, header forwarding, tool policy and grants | `llm_proxy` is a platform-owned singleton; generic create/get/update/delete explicitly reject it. Do not recreate that singleton. | Native and both-scope create/update/drift-repair/delete passed |
| Plugins and external skills | Versioned plugin package files and metadata; source repository/ref/subdirectory plus explicit synchronization configuration | Plugin-derived skills are children of the installed package, not independent manual skills. Discovery, preview, import commands and sync runs are alternate operations or transient observations. A pinned source is desired state; each periodic sync run is not. | Desired; implementation pending |
| Apps and tool bindings | App HTML/versioned source, metadata, environment, grants, enable/lock/fullscreen controls; individual tool binding | Rendering diagnostics, screenshots, open-in-chat, per-user pinning and historical version restoration are commands/preferences. Versions are immutable revisions of the app identity. | Desired; implementation pending |
| Project files and apps | Explicit project/app association; project-owned uploaded content | Instructions are already a project attribute. Project file upload/list exists, but no project-file delete endpoint is declared; find the authoritative attachment deletion contract before exposing a resource that promises normal deletion. Avoid owning all project files implicitly. | App binding desired; file deletion contract investigation required |
| Connectors and knowledge associations | Persistent connector type/configuration/credentials/schedule/enabled/permission-sync settings; knowledge-base membership; member overrides keyed by external account | OAuth start/callback remains interactive authorization. Sync, force-resync, connection tests, run cancellation and indexed connector documents are execution/derived state. The provider must preserve redacted secrets on unrelated updates and use existing authorized connections. | Desired; implementation pending |
| Knowledge documents and directories | Uploaded file content with a stable identity/hash and directory association; named directories | Index jobs and parser results are derived asynchronous state; promotion from a chat attachment is an alternate creation operation. Deleting a directory moves files to repository root rather than deleting them. | Directory native and both-scope lifecycles passed; file content resource pending |
| Remote A2A agents | Persistent external agent source, name, description and credentials; authoritative external delegation set | Agent-card inspection and outbound runs are observations/executions. Remote registration and delegation association are distinct persistent identities. | Native and both-scope lifecycles passed, including connection references, metadata/source drift repair, secret preservation/clearing, empty assignments and creation grants; outbound runs are not invoked |
| Service accounts and tokens | Non-human identity, role, disabled state, labels, grants; separately revocable credential with metadata, expiry and explicit replacement/rotation | Token use telemetry is computed. Secret values are returned once; imports adopt metadata without fabricating a secret. Credential creation in acceptance tests is confined to the disposable local stack. | Native and both-scope lifecycles passed, including secret-once publication, authentication, disablement and revocation |
| Virtual and OAuth clients | Virtual LLM API key routing/billing/spend caps; one unified managed OAuth client with explicit scopes, grant type, gateway/provider bindings and secret-once state | `McpOauthClientModel` and `LlmOauthClientModel` are compatibility facades over `ManagedOauthClientModel`. Cover their capabilities through the unified client rather than introducing competing owners for the same row. User consent, authorization/device-login callbacks and token redemption remain interactive operations. | Virtual keys and one unified OAuth client are implemented; six native cases and twelve both-scope records pass, including routing/billing/expiry preservation, empty clears, both grant modes, initial grants and in-place secret rotation. Interactive authorization-code consent remains outside the resource lifecycle |
| GitHub configurations | Registration of an already-created GitHub App installation using supplied IDs/key; storage of an existing PAT under a managed name | These APIs do not provision GitHub accounts, permissions or installations. Manifest creation, repository creation and installation consent belong to the external service's authorization flow. Inline credentials are sensitive/write-only and must survive metadata updates. | Both storage/registration families pass native creation/import/metadata/credential-change/no-op/delete tests and both-scope reconciliation. Metadata changes do not resend credentials; synthetic test references do not authenticate to or provision GitHub |
| Guardrails and OpenAPPA | Guardrails deployment settings and version-checked policy source; OpenAPPA battery packages/installs, credential bindings and versioned policy-test files; existing-repository synchronization settings | Annotation, policy evaluation, helper consultation, test runs/previews, remedy activity and coverage/yell logs are observations/executions. GitHub app/repository provisioning is an external setup action, not implicit resource creation. OpenAPPA core code remains in its separate repository. | Desired; implementation pending |
| ChatOps configuration and bindings | Configuration referencing already-authorized Slack/Teams/Telegram apps; persistent agent/channel/DM bindings where the API exposes their identity and readable configuration | OAuth callbacks, app provisioning/conversion/migration, channel join/discovery commands, ngrok quickstart tunnels, account linking and one-time link codes are setup or user activity. A managed binding must not silently join channels, send messages or create third-party apps. | Desired; inspect read/secret contracts before implementation |
| Hooks and site notifications | Agent event hook file/content/dependencies/enabled state; organization site-notification configuration as a single authoritative slot | Applying a hook declares it without executing it. Site notifications are persistent announcements, not a generic outbound messaging API; use only an isolated test organization for acceptance. Active/latest notification reads differ and must be handled explicitly. | Hook native and both-scope lifecycles passed; notification implementation pending |
| Defaults and Vault bindings | Default user cost limit (organization/global or per environment); per-kind default environment assignments; team-to-existing-Vault-folder binding | Existing organization settings already own the default deployment environment's own properties. Per-kind resource defaults are a different mapping. Vault connectivity tests and secret listing are observations; never create Vault folders/secrets implicitly. | Default-limit, per-kind environment defaults and team Vault-folder binding native and both-scope lifecycles passed; unrelated default slots and external Vault secrets are preserved |
| Alert mutes and skill share links | Alert policy keyed by installation/catalog plus alert kind and expiration; revocable share link with immutable membership/expiry and sensitive secret-once delivery URL | Expiry and revocation are observable lifecycle events. Do not expose raw token rotation as a separate long-lived identity; replace the link explicitly. These are deliberate configuration choices, not a reason to grant new public access during provider upgrade. | Desired; implementation pending |

## Field review

`request-field-review.json` classifies every occurrence in the 90-row baseline: 61 unique resource/field pairs, including repeated create/update occurrences. The review found two controls within that baseline: gateway `access_all_subagents` and personal installation `user_id`. A third control, installation `hibernation_mode`, lives on a previously unused reinstall endpoint outside the baseline. All three now have source implementations and native acceptance regressions.

The remaining baseline occurrences are manually encoded existing capabilities, derived selectors/concurrency values, lifecycle/server-owned state, fields belonging to another agent subtype, a legacy alias, or capabilities owned by a separate resource. Their per-field rationale and source locations are preserved in `request-field-review.md`; they are not counted as missing implementation.

## Release evidence boundaries

The baseline 29-family runtime proof must remain tied to its recorded native/controller hashes and API snapshot. New native tests, new both-scope tests, final full-suite/migration repetition and full runtime image/xpkg tests need their own candidate hashes. No static classification or generated CRD closes a runtime test. No desired row is excluded merely because its implementation is larger or requires an enterprise fixture.

Daily sync stays disabled until supported setup and a manually reviewed PR dry run pass. This design does not authorize automatic merging of future synchronization PRs.
